# Static site for SEO/AEO — design

Date: 2026-09-13
Status: approved

## Problem

`dist/osint-explorer.html` is a single self-contained, client-rendered offline
page (by design — see README "Quick start"). That's the right shape for the
offline/CLI use case, but it's the wrong shape for discovery: every tool's
name, description and URL only exists inside a JS-injected JSON payload, there
is exactly one URL for 700+ entries, and there's no structured data. Crawlers
that don't execute JS (and most answer-engine crawlers) see an empty shell.

This adds a second, independent build target: a real static, multi-page site
suitable for hosting on GitHub Pages, optimized for search/answer-engine
discovery and citation. It does not replace or modify the offline single-file
app or the CLI.

## Decisions (from brainstorming)

- Hosting: GitHub Pages, project site at `https://halans.github.io/osint-explorer-v2/`
  (repo: `halans/osint-explorer-v2`, default branch `master`).
- Page granularity: category pages only (~15 pages), not per-tool pages.
- The interactive single-file explorer is **not** published on the hosted
  site — the static site links back to the GitHub repo for it instead.
- Retired tools appear on category pages with a "Retired" badge (not omitted).

## Site structure & URLs

```
site/                              (generated by `npm run build:site`; gitignored, never committed)
  index.html
  sitemap.xml
  robots.txt
  404.html
  assets/style.css
  category/
    <slug>/index.html              one directory per category (15 total)
```

- Category slugs: `slugify(category.name)` — lowercase, non `[a-z0-9]` runs
  collapsed to `-`, trimmed; deduplicated with a `-2`, `-3`, ... suffix on
  collision (defensive; no real collisions in the current 15 categories).
- All internal links are **relative** (`category/<slug>/`, `../../`,
  `../../assets/style.css`) so the site works under any base path without
  reconfiguration.
- Only `<link rel="canonical">`, Open Graph URLs, `sitemap.xml`, and
  `robots.txt` use the absolute base URL
  (`https://halans.github.io/osint-explorer-v2/`), defined as one constant at
  the top of `scripts/build-site.mjs`.

## Homepage (`site/index.html`)

- `<h1>OSINT Explorer</h1>` + a plain-text lead paragraph built from live
  `ds.stats`/`ds.generatedAt` (not hand-written), e.g.: "OSINT Explorer is a
  directory of {live} link-checked open source intelligence tools, datasets,
  and live feeds across {categories} categories — covering geolocation,
  people search, corporate profiling, area monitoring, and more. Every entry
  is health-checked and described."
- Stats strip: tools / live / categories / last-updated date.
- A card per category: name, tool count, one auto-generated sentence (count +
  up to a few subcategory names), linking to `category/<slug>/`.
- Closing note linking back to `https://github.com/halans/osint-explorer-v2`
  for the interactive explorer and CLI.
- `<head>`: canonical, meta description (trimmed lead sentence), Open Graph
  (`og:title`, `og:description`, `og:type=website`, `og:url`), Twitter card
  (`summary`), JSON-LD `WebSite` + a `CollectionPage`/`ItemList` of the 15
  categories.

## Category page (`site/category/<slug>/index.html`)

- Breadcrumb "Home / {Category}" (visual + `BreadcrumbList` JSON-LD).
- `<h1>{Category name}</h1>` + one auto-generated lead sentence (count +
  subcategory list).
- Tools grouped under `<h2>{Subcategory}</h2>` sections using the existing
  `subcategory` field, rather than one flat list — this keeps large
  categories (up to 174 tools) legible and gives each subcategory its own
  citable anchor.
- Tool card: name linked to its external `url`, hostname, description (or
  "No description verified yet." when null, matching the interactive app's
  copy), badges for kind/access/targets/regions, "Retired" badge when
  `retired: true`.
- Outbound link `rel`: `retired: true` → `rel="nofollow noopener noreferrer"`
  (the dataset only retires on a confirmed 404/410 health check, so this is
  the one clean signal to withhold link authority from); everything else →
  `rel="noopener noreferrer"` and is followed (statuses like `bot-walled` or
  `unreachable` don't necessarily mean the resource is bad — just that the
  automated check couldn't confirm it).
- `<head>`: canonical, meta description, OG/Twitter (title =
  `"{Category} — OSINT Explorer"`), JSON-LD `CollectionPage` containing an
  `ItemList` of the tools in that category.

### JSON-LD kind mapping

| `kind` values | schema.org type |
|---|---|
| `dataset`, `database`, `feed` | `Dataset` |
| `software`, `web-tool`, `map`, `search`, `api` | `SoftwareApplication` |
| `directory`, `reading` | `CreativeWork` |
| anything else | `Thing` |

## Build script — `scripts/build-site.mjs`

Same style as `scripts/build.mjs`: small, pure, exported functions (so
they're independently testable, the way `inlineEngine` already is), plus a
top-level script body.

Exported functions:
- `slugify(name)`
- `mapKindToSchemaType(kind)`
- `renderToolCard(tool)`
- `renderCategoryPage(category, tools, { baseUrl, generatedAt })`
- `renderHomePage(dataset, categories, { baseUrl })` (`categories` = `[{ name, slug, count, subcategories }]`)
- `buildSitemap(urls, { baseUrl, lastmod })`

Script body: load `data/tools.enriched.json`, group tools by category
(respecting `retired`, kept per section above), slugify + dedupe category
names, render every page, write `site/` (`mkdirSync(recursive: true)`),
write `sitemap.xml`, `robots.txt`, `404.html`, copy `assets/style.css`.

New npm script: `"build:site": "node scripts/build-site.mjs"`. Independent
of `npm run build` (the offline single-file app) — both read
`data/tools.enriched.json`; neither depends on the other's output.

`site/` is added to `.gitignore` (generated CI artifact, never committed —
unlike `dist/`, which is a distributed offline artifact).

## CI deploy — `.github/workflows/pages.yml`

Triggers on push to `master`. Steps: checkout → `actions/setup-node@v4`
(node 20) → `npm run build:site` → `actions/upload-pages-artifact@v3`
(path: `site`) → `actions/deploy-pages@v4`. No install step (zero
dependencies).

One manual, one-time step this doc can't perform: in the GitHub repo,
**Settings → Pages → Source → "GitHub Actions"**.

## Sitemap / robots / 404

- `sitemap.xml`: home + all 15 category URLs, each `<lastmod>` =
  `ds.generatedAt` (date only).
- `robots.txt`: `Allow: /` + `Sitemap:` line with the absolute sitemap URL.
- `404.html`: same stylesheet, a heading, a link home.

## Tests — `test/site.test.mjs`

Following the existing `node --test`, no-mocks convention. Imports the pure
functions from `build-site.mjs` and asserts against the real dataset:
- slugs are unique across all real categories
- every category page's JSON-LD parses, and its `ItemList` length matches
  the tool count for that category
- retired tools get `rel="nofollow ..."`; non-retired tools don't
- the sitemap contains exactly one `<url>` per category plus the homepage

## Out of scope (explicitly)

- Per-tool pages (rejected in brainstorming — thin-content risk without
  per-tool inline detail beyond what's already on the category page).
- Publishing the interactive single-file app on the hosted site.
- Any client-side JS on the static site (fully static by design, for
  crawler robustness).
- Hand-written per-category copy (lead sentences are auto-generated from
  the dataset; can be revisited later without changing this design).
